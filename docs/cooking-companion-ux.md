## Comparative research (Australian iOS store, retrieved 27 Nov; snapshots can lag; not Android scores)

- [MEATER](https://apps.apple.com/au/app/meater-smart-meat-thermometer/id1157416022): 4.7/5, 11K ratings. Guided food/cut/doneness selection, estimate, rest, history, multiple probes. Review complaints about dropouts, accidental stop/resume and inflexible multi-stage cooks. Preserve cook state across disconnect and add flexible stages.
- [FireBoard](https://apps.apple.com/au/app/fireboard/id1049169343): 4.7/5, 50 ratings. Multi-channel monitoring, graphs. [Drive Programs](https://www.fireboard.com/blog/app-basics-2-drive-programs/) and [Analyze](https://www.fireboard.com/blog/are-you-using-fireboard-analyze/) provide stage and historical comparison references. These are other hardware capabilities, not evidence AKORN can execute them.
- [Combustion Inc.](https://apps.apple.com/au/app/combustion-inc/id1658858290): 5.0/5, 44 ratings. Predicted finish, distinct core/surface/ambient sensing. Do not infer those channels exist on AKORN or substitute an estimate for measurement.
- [Kamado Joe](https://apps.apple.com/au/app/kamado-joe/id1658209697): 4.7/5, 63 ratings. Cooking graphs/history, device status, recipe filters. [Recipe catalogue](https://www.kamadojoe.com/blogs/recipes) for inspiration, link out or create original recipes with source provenance; no bulk copying proprietary text.
- [ThermoWorks](https://apps.apple.com/au/app/thermoworks/id1503955408): 4.7/5, 107 ratings. Device/channel management and notifications; review highlights graph resolution and connectivity. Separate traces, consistent Celsius, no interpolation across lost telemetry.
Small review samples except MEATER; not a formal usability study. Learn patterns rather than clone.

## Product UX (proposed)

Android primary, phone and dedicated low-spec Lenovo tablet; lightweight PWA secondary. Four primary destinations: Cook (current session/quick monitor), Recipes (browse/filter/manual), Devices (add grill/probes, assign names/roles, connectivity), History (notes/photos/graphs/repeat). Contextual Ask cooking assistant, not chatbot as entry point. Default on launch: active cook if any, otherwise simple start recipe/manual/quick monitor. Setup wizard discovers only supported devices after user action, remembers approved selection locally; manual IP/name remains Advanced. Do not scan unrelated network devices. Show connection source, last updated, no false live values, demo unmistakable. Recover cook records without pretending to reconnect automatically or invent missing data. Large touch targets (48dp), sunlight-friendly contrast, text scaling, TalkBack, portrait/landscape, tablet dashboard and optional keep-screen-on. Probe cards named by purpose (Brisket / Chicken / grate), reported vs planned target explicit, disabled/disconnected text not only color. Charts accessible, time range, selectable traces, event markers, no fake ETA. Show next action near top, alert history and acknowledgement separate from physical alarm. No button that appears to actuate when command unavailable. Start with current demo, do not redesign transport.

## Recipes and sessions

Store local structured versioned recipes and immutable session snapshots (SQLite on Android; simple portable JSON format). Fields: title, method, cut/food, weight/thickness inputs, accessories (heat deflector/grate/pizza stone/rotisserie), indirect/direct setup, fuel/wood guidance, steps, chamber target range and confirmed probe threshold, trigger type, min/max duration guidance, user check, source/date, food safety notes, required hardware, serving/rest guidance and optional photo. Include original seed recipes after source verification, not copied text. Recipe categories: low-and-slow brisket/pork shoulder/ribs; direct grilling steaks/burgers; reverse sear; roast poultry/lamb; hot smoke fish; pizza/bread; vegetables; Dutch oven/braising; sides/dessert. Not all cooking modes safe for all accessories; compare actual E6480 manual. No cold smoking until validated food safety method. Start with 6-10 curated templates across methods, with source links, metric units, optional manual session. No universal cook time by weight; thickness, initial temp and actual readings matter. Serve-time planner gives range and buffer, never guarantee. Timeline events for preheat, wrap, spritz, flip, vent/accessory changes, rest. Save measurements, notes/photo, outcomes and repeat; capture user feedback.

A deterministic stage engine (simulation only initially): plan with explicit triggers (elapsed time, validated named food probe crosses target for duration, user action), states pending/active/awaiting confirmation/completed/paused, stable freshness checks, no phase advancement on bad/stale/unknown measurement, no automatic resume after disconnect. Human confirms physical actions and manually adjusts OEM controller. Log actual vs intended targets and stage reasons. Visual plan e.g. reverse sear: indirect low heat -> verify food probe -> remove food/confirm reconfiguration -> direct sear -> verify core temp -> rest. Never assert chamber can cool rapidly; closing dampers or changing setpoint does not instantly cool charcoal. No command writes, fan override, power control or smart plug cut. Future controlled target automation a separate design/gate after actual protocol/firmware and cold supervised test plus owner authorisation; OEM feedback loop/interlocks retained, independent validated rule limits, manual override, no blind retries/automatic rearm, operator present. Model never controls fan or commands hardware.

## External probes

Normalize a source-aware TemperatureSample: device_id, channel_id, user label/role, current_c, measured_at/received_at, freshness, availability, model/capabilities, battery if supported, quality and source. Separate ambient/grate vs food/core vs controller-estimated chamber temperature, never silently average or swap roles. Keep stable local IDs, no secret network metadata in public logs. Reuse tested integrations where licences allow:
- [HA INKBIRD](https://www.home-assistant.io/integrations/inkbird/) local BLE supports IBT-2X, IBT-4XS, IBT-6XS among others; model-specific.
- [inkbird-ble](https://inkbird-ble.readthedocs.io/en/latest/usage.html) parser reference; some models use GATT notifications instead of advertisements. Identify owner's exact model first; Wi-Fi vendor APIs and other brands not assumed. Start with local HA/gateway adapter or native BLE for one verified model after cold AKORN acceptance; fake multi-probe fixtures before any real connection. MQTT module today message-only, not broker connected; no LAN exposure.
- Future adapters for supported MEATER, Combustion, ThermoWorks, FireBoard, generic MQTT/manual reading if verified. One AKORN transport owner, each external device read-only and explicitly assigned. Handle stale, lost, disagreement, thermal ratings, disconnect, conflicting role, manual swap; notifications require verified background delivery. External probe never directly drives fan or bypasses controller.

## Cooking assistant (proposed, optional)
Deterministic recipes + search + food safety rules + telemetry trend estimation work offline without model. Optional assistant answers natural-language questions using selected source-backed recipes, device manual, current normalized readings, cook plan and stage events. Use local model on capable phone first, optional Hermes/local computer adapter later, opt-in cloud only with explicit privacy/cost controls. [Google AI Edge Gallery](https://gemma.ai/deployment/ai-edge-gallery/) is a practical test harness for on-device Gemma; [LiteRT](https://developers.google.com/edge/litert) supports on-device deployment. Benchmark small text quantized model on actual phone, no bundled model, separate download and memory/storage/latency test. Do not assume a 2GB tablet can sustain model + monitoring; it should always operate without AI. Camera: recognise cut/package label as suggestion, OCR weight/units if visible, user confirms measured weight/cut/thickness, allergies if relevant. Never infer exact weight from unscaled image, core temp/doneness or food safety from appearance; ask user to use scale/thermometer. Camera/model optional, photos private/local; no cloud upload without explicit consent. LLM returns candidate structured plan/explanation only. Validate all numeric suggestions against curated rules, hardware/accessory limits and confirmed facts; reject uncertainty/unsafe plans, cite trusted sources, require confirmation. Australian Centre for Disease Control [foodborne illness prevention](https://www.cdc.gov.au/advice/preventing-foodborne-illness) recommends at least 75°C in centre for poultry, minced/rolled meat and liver, and leftovers reheated to 75°C; [FSANZ](https://www.foodstandards.gov.au/consumer/prevention-of-foodborne-illness/food-safety-basics). Distinguish recipe quality target from minimum safety requirements; no unvalidated time/temp pasteurisation claims. Existing manual limits in docs/deep-research-2026-11-26.md take precedence. Temperature recommendations are not a substitute for measuring with thermometer. Never delegate food safety, alerts, stage transitions or hardware control to probabilistic model.

## Phased acceptance and backlog
P0: keep current physical owner acceptance as gate; review Android visual patch (build/lint, 320dp, large text, portrait/landscape, TalkBack, actual Lenovo performance), check no regressions in demo, fresh/stale, permissions and transport. Retain APK from before UI patch for owner checks. No new execution automatically.
P1: after owner acceptance or bounded demo-only scope approval, simple Cook/Recipes/Devices/History, local session persistence and simulated multi-stage guides, curated recipe templates + tests, graph and resume. Single screen first, then progressive navigation; no giant framework. Add optional photo and named probes. Accept if beginner starts demo/quick cook in 2 taps, selects recipe in <=4 navigation steps (excluding input), finds current/target/next action within 5s; test offline, interrupted cook, stale/unavailable, accessibility and small screen.
P2: read-only one actual INKBIRD model adapter and simulated extra probes, deterministic estimates with uncertainty and no estimate if insufficient data, local alerts only after foreground/background behavior verified. No automatic action.
P3: optional on-device assistant proof (benchmark phone, memory/thermal/latency, no interference with monitor; safe fallback; test malicious/ambiguous user/photo input and source attribution), model optional. Compare local versus remote in simulator.
P4: separate explicit authorisation for future bounded target commands after physical verification, independent safety review and safe supervised test; no direct LLM/fan control. Recipe stages remain advisory unless independently accepted.
