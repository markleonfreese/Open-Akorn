## Comparative research (Australian iOS store, retrieved 27 Nov; snapshots can lag; not Android scores)

- [MEATER](https://apps.apple.com/au/app/meater-smart-meat-thermometer/id1157416022): 4.7/5, 11K ratings. Guided food/cut/doneness selection, estimate, rest, history, multiple probes. Review complaints about dropouts, accidental stop/resume and inflexible multi-stage cooks. Preserve cook state across disconnect and add flexible stages.
- [FireBoard](https://apps.apple.com/au/app/fireboard/id1049169343): 4.7/5, 50 ratings. Multi-channel monitoring, graphs. - [Combustion Inc.](https://apps.apple.com/au/app/combustion-inc/id1658858290): 5.0/5, 44 ratings. Predicted finish, distinct core/surface/ambient sensing. Do not infer those channels exist on AKORN or substitute an estimate for measurement.
- [Kamado Joe](https://apps.apple.com/au/app/kamado-joe/id1658209697): 4.7/5, 63 ratings. Cooking graphs/history, device status, recipe filters. - [ThermoWorks](https://apps.apple.com/au/app/thermoworks/id1503955408): 4.7/5, 107 ratings. Device/channel management and notifications; review highlights graph resolution and connectivity. Separate traces, consistent Celsius, no interpolation across lost telemetry.
Small review samples except MEATER; not a formal usability study. Learn patterns rather than clone.

## Product UX (proposed)

Android primary, phone and dedicated low-spec Lenovo tablet; lightweight PWA secondary. Four primary destinations: Cook (current session/quick monitor), Recipes (browse/filter/manual), Devices (add grill/probes, assign names/roles, connectivity), History (notes/photos/graphs/repeat). Contextual Ask cooking assistant, not chatbot as entry point. Default on launch: active cook if any, otherwise simple start recipe/manual/quick monitor. Setup wizard discovers only supported devices after user action, remembers approved selection locally; manual IP/name remains Advanced. Do not scan unrelated network devices. Show connection source, last updated, no false live values, demo unmistakable. Recover cook records without pretending to reconnect automatically or invent missing data. Large touch targets (48dp), sunlight-friendly contrast, text scaling, TalkBack, portrait/landscape, tablet dashboard and optional keep-screen-on. Probe cards named by purpose (Brisket / Chicken / grate), reported vs planned target explicit, disabled/disconnected text not only color. Charts accessible, time range, selectable traces, event markers, no fake ETA. Show next action near top, alert history and acknowledgement separate from physical alarm. No button that appears to actuate when command unavailable. Start with current demo, do not redesign transport.

## Recipes and sessions

Store local structured versioned recipes and immutable session snapshots (SQLite on Android; simple portable JSON format). Fields: title, method, cut/food, weight/thickness inputs, accessories (heat deflector/grate/pizza stone/rotisserie), indirect/direct setup, fuel/wood guidance, steps, chamber target range and confirmed probe threshold, trigger type, min/max duration guidance, user check, source/date, food safety notes, required hardware, serving/rest guidance and optional photo. Include original seed recipes after source verification, not copied text. Recipe categories: low-and-slow brisket/pork shoulder/ribs; direct grilling steaks/burgers; reverse sear; roast poultry/lamb; hot smoke fish; pizza/bread; vegetables; Dutch oven/braising; sides/dessert. Not all cooking modes safe for all accessories; compare actual E6480 manual. No cold smoking until validated food safety method. Start with 6-10 curated templates across methods, with source links, metric units, optional manual session. No universal cook time by weight; thickness, initial temp and actual readings matter. Serve-time planner gives range and buffer, never guarantee. Timeline events for preheat, wrap, spritz, flip, vent/accessory changes, rest. Save measurements, notes/photo, outcomes and repeat; capture user feedback.

A deterministic stage engine (simulation only initially): plan with explicit triggers (elapsed time, validated named food probe crosses target for duration, user action), states pending/active/awaiting confirmation/completed/paused, stable freshness checks, no phase advancement on bad/stale/unknown measurement, no automatic resume after disconnect. Human confirms physical actions and manually adjusts OEM controller. Log actual vs intended targets and stage reasons. Visual plan e.g. reverse sear: indirect low heat -> verify food probe -> remove food/confirm reconfiguration -> direct sear -> verify core temp -> rest. Never assert chamber can cool rapidly; closing dampers or changing setpoint does not instantly cool charcoal. No command writes, fan override, power control or smart plug cut. Future controlled target automation a separate design/gate after actual protocol/firmware and cold supervised test plus owner authorisation; OEM feedback loop/interlocks retained, independent validated rule limits, manual override, no blind retries/automatic rearm, operator present. Model never controls fan or commands hardware.

## External probes

Normalize a source-aware TemperatureSample: device_id, channel_id, user label/role, current_c, measured_at/received_at, freshness, availability, model/capabilities, battery if supported, quality and source. Separate ambient/grate vs food/core vs controller-estimated chamber temperature, never silently average or swap roles. Keep stable local IDs, no secret network metadata in public logs. Reuse tested integrations where licences allow:
- [HA INKBIRD](https://www.home-assistant.io/integrations/inkbird/) local BLE supports IBT-2X, IBT-4XS, IBT-6XS among others; model-specific.
- [inkbird-ble](https://inkbird-ble.readthedocs.io/en/latest/usage.html) parser reference; some models use GATT notifications instead of advertisements. Identify owner's exact model first; Wi-Fi vendor APIs and other brands not assumed. Start with local HA/gateway adapter or native BLE for one verified model after cold AKORN acceptance; fake multi-probe fixtures before any real connection. MQTT module today message-only, not broker connected; no LAN exposure.
- Future adapters for supported MEATER, Combustion, ThermoWorks, FireBoard, generic MQTT/manual reading if verified. One AKORN transport owner, each external device read-only and explicitly assigned. Handle stale, lost, disagreement, thermal ratings, disconnect, conflicting role, manual swap; notifications require verified background delivery. External probe never directly drives fan or bypasses controller.

## Cooking assistant (proposed, optional)
Deterministic recipes + search + food safety rules + telemetry trend estimation work offline without model. Optional assistant answers natural-language questions using selected source-backed recipes, device manual, current normalized readings, cook plan and stage events. Use local model on capable phone first, optional Hermes/local computer adapter later, opt-in cloud only with explicit privacy/cost controls. [Google AI Edge Gallery](https://gemma.ai/deployment/ai-edge-gallery/) is a practical test harness for on-device Gemma; [LiteRT](https://developers.google.com/edge/litert) supports on-device deployment. Benchmark small text quantized model on actual phone, no bundled model, separate download and memory/storage/latency test. Do not assume a 2GB tablet can sustain model + monitoring; it should always operate without AI. Camera: recognise cut/package label as suggestion, OCR weight/units if visible, user confirms measured weight/cut/thickness, allergies if relevant. Never infer exact weight from unscaled image, core temp/doneness or food safety from appearance; ask user to use scale/thermometer. Camera/model optional, photos private/local; no cloud upload without explicit consent. LLM returns candidate structured plan/explanation only. Validate all numeric suggestions against curated rules, hardware/accessory limits and confirmed facts; reject uncertainty/unsafe plans, cite trusted sources, require confirmation. Australian Centre for Disease Control [foodborne illness prevention](https://www.cdc.gov.au/advice/preventing-foodborne-illness) recommends at least 75°C in centre for poultry, minced/rolled meat and liver, and leftovers reheated to 75°C; [FSANZ](https://www.foodstandards.gov.au/consumer/prevention-of-foodborne-illness/food-safety-basics). Distinguish recipe quality target from minimum safety requirements; no unvalidated time/temp pasteurisation claims. Existing manual limits in docs/deep-research-2026-11-26.md take precedence. Temperature recommendations are not a substitute for measuring with thermometer. Never delegate food safety, alerts, stage transitions or hardware control to probabilistic model.

## Release boundary and modular architecture — owner decision, 27 Nov 2026 14:09 AWST

This section supersedes earlier phase descriptions where inconsistent. Owner explicitly requires the full UI/UX improvement in the current version, with other cooking enhancements deferred into optional modules in the next version. Do not create two independent apps or fork the monitoring code.

### V1 Core (current draft PR #1)
Finish the current Android and PWA monitoring experience: temperature-first dashboard, high contrast, responsive portrait/landscape, large text and touch targets, plain-language connection setup and recovery, demo-first onboarding, visible source/freshness/connection and reported fan/alarm, two named-by-channel probe cards, offline operation, no clutter. Improve Bluetooth selection only with verified device discovery, explicit user choice and manual fallback; preserve one transport owner, permissions, stale clearing and existing safety boundary. Do not add recipe/session/history, external probes, AI, camera, broker wiring or programme automation to this release. Validate new layout on small phones and Lenovo Android 10/2 GB provisional baseline, including text scaling and TalkBack; test demo, disconnect, malformed/stale data, and cold-grill hardware gate. Preserve existing Gradle/native Views and lightweight PWA. Finish/rebuild owner APK; preserve actual CI/build evidence and artifact provenance. V1 release is a product milestone, not a declaration that current 0.1.0 debug preview is production-ready. No independent plugin framework or packaging migration required in v1.

### V2: one app, optional feature modules
Use ordinary Gradle feature/library modules and small versioned interfaces when needed, not a runtime-loaded third-party plugin system, separate app forks or heavy orchestration framework. Keep the existing monitor, transport, normalized readings and safety checks in core. Features consume a read-only snapshot/session interface and register UI destinations only when enabled; core never depends on optional modules. Keep a stable app identity and data format, per-device local settings, feature availability (installed/enabled/device-capable), and fail-safe fallback. Add a simple Settings > Features screen once there is a feature to enable. Start with compile-time module boundaries and lazy initialization. Feature toggles alone do not reduce installed APK size; use separate optional assets/model downloads first, consider core/full build variants from the same repo and package identity only if measured size warrants it and signing/update path is compatible; Play dynamic delivery is not a prerequisite and would require separate distribution decision. No downloaded executable plugins, unrestricted code execution or mandatory cloud/account.

Proposed modules: recipes (curated versioned content packs); guided cooking (deterministic stages and timers, advisory only); journal (bounded local history, graph, optional photo); external probes (read-only model-specific adapters); cooking assistant (optional on-device text inference); camera assistant (optional recognition/OCR); home integration (optional gateway/MQTT); smart programmes (future independently validated deterministic target proposals, live actuation separately authorised). Model inference/assets must not be bundled in Core or run at startup; download only on explicit opt-in, inspect storage/RAM/device support first, provide removal and no-AI fallback. No automatic cloud upload or model command path. Lightweight tablet defaults to Core; capable phone may enable modules individually. PWA secondary shares the status contract, not necessarily every native feature. Tablet/phone multi-device sharing needs a separately approved authenticated gateway design; no simultaneous direct-controller client assumption.

Acceptance targets (proposed, measure rather than claim): Core APK <=15 MB, cold start <=3 s, steady PSS <=80 MB on intended 2GB tablet, approximately 1 Hz telemetry, no optional module initialization when disabled, no AI or camera permission/download in Core, no dependency on optional storage/network, offline monitoring remains usable if any module fails. Existing preview ~2.7 MB is baseline, not proof of performance. Test with all modules off and selectively enabled as modules arrive. Use a single shared protocol fixture set and avoid duplicating transport or safety logic.

Sequence: finish and validate v1 UI plus owner cold-grill acceptance; then separately scoped v2 modules, starting with low-cost recipes/guided cooking and journal, followed by model-specific probe adapters and optional AI. No live writes, fan override, automatic provisioning, unsafe control, merge, deployment or paid usage without explicit authority. Existing safety guidance and physical acceptance gate unchanged. No new implementation or agent dispatch from this architecture note.

### V2 cooking assistant: bring your own API key (BYOK)
Owner requested BYOK as an additional optional inference mode, alongside disabled/offline rules, on-device inference and separately secured local-server inference. Provider adapters should support user-selected models, capability discovery/validation where available, explicit opt-in connection tests, timeouts/cancellation, redacted error reporting, usage tracking and configurable request/token budgets. Start with one provider adapter and an independently testable common interface; OpenAI, Gemini, Anthropic and compatible local endpoints are candidates, not implemented support. No provider dependency in V1/Core. Keep keys encrypted with Android Keystore-backed storage (key material protected by Keystore; encrypted credential data excluded from backup/export); never embed shared keys, include secrets in prompts/logs, commit credentials, or expose keys to browser scripts. Delete credentials on removal. Require HTTPS for remote provider endpoints; local endpoints require separate approved secure design. Cloud processing disabled by default; preview what cook context/photos are sent and require explicit consent before image upload; do not transmit unrelated network/device metadata. No silent paid fallback or repeated billable retries; warn API charges may be separate from chat subscription. Budget estimates are advisory unless actual provider-enforced caps exist. Provider/model failure must not interrupt monitoring or deterministic cooking guidance. LLM cannot directly invoke controller commands, modify safety rules or certify food safety. Tests: fake providers, key redaction/deletion, offline fallback, budget limits, rejected unsafe suggestions and optional module disabled. Defer implementation to V2; no API keys requested, created or tested in this update.

### 28 November 2026 — legacy app parity request

The owner expanded the current work to cover the public Char-Griller app's core local features. `docs/legacy-app-parity.md` owns the feature-by-feature audit and server-replacement investigation. A local-only timer, bounded live graph and bounded local session graphs are available in Android and PWA; this implements the legacy Session tab within the current parity goal, while recipes and richer journal/history remain future scope. Android supports up to 12 locally stored named Wi-Fi/Bluetooth profiles; loading a profile never connects automatically, and connecting replaces the current single session. Session history retains up to 8 sessions with samples about once per minute, excludes simulation and can be cleared. The timer never sends a timer command and cannot promise an alert when the app/page is suspended or closed. Physical profile switching and session persistence remain unverified on owner devices.

The app's setpoint/fan command parity remains blocked by the existing physical acceptance and separate actuation-authorization gate. Do not add a write path, provision Wi-Fi, reset the controller, or imitate Char-Griller cloud endpoints. The supported replacement path is Open-Akorn's own local-only client/gateway using the controller's direct local protocol. The expanded parity request does not relax the factory-controller safety boundary.
