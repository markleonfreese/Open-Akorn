User decision: support Dad's Android phone and repurpose his unused low-spec Lenovo tablet as a dedicated household display/control interface. Exact device models, Android versions and RAM are not confirmed; use Android 10/API 29 and 2 GB RAM as provisional design/test baseline, not verified hardware inventory. Future household IoT is an extension opportunity, not current MVP scope.

## Offline prototype implementation — 26 November 2026

The Android module builds a 2.81 MB debug APK using Kotlin and Android Views, with minSdk 29, compileSdk 36 and targetSdk 35. Current PR head is `80781d3`; Android profile UI landed at `dbc68e8`; TCP/Bluetooth transport baseline is `ce89fc8`. It includes shared-fixture demo, explicit private-IPv4 TCP monitoring, user-triggered filtered BLE discovery with explicit selection and manual advertised-name fallback, Celsius readings, five-second freshness, and up to 12 saved Wi-Fi/Bluetooth profiles. Profiles are device-local and excluded from Android backup; loading a profile does not connect, and Connect replaces the single current session. The dashboard prioritizes temperatures, separates reported fan/alarm cards, highlights active alarms and has a two-column landscape tablet layout. Telemetry uses localized resources, polite live regions and accessibility headings; connection fields opt out of autofill. The manual TCP field shows an example private IPv4 and requests a URI keyboard. Exact-head run [46142948325](https://github.com/markleonfreese/Open-Akorn/actions/runs/46142948325) passed Android tests/Lint/APK packaging and Python 3.11/3.13; lint reports 12 warnings and zero errors. No Android device was attached; profile workflow, scan/connect behavior, target layout, font scaling, TalkBack, lifecycle behavior, physical BLE/TCP compatibility and Lenovo performance remain unverified.

The app disconnects when backgrounded. It requests only foreground Bluetooth permissions: Android 12+ uses Nearby Devices scan/connect permissions; Android 10/11 requests foreground location permission for BLE scanning. It supports up to 12 locally saved, named Wi-Fi/Bluetooth connection profiles. Profile selection only loads the address/name into the setup form; the operator explicitly taps Connect, which stops the current session before opening the next one. Profiles store no Bluetooth MAC address, are not included in Android backup, and never auto-connect. Only one direct grill connection is active at a time. No background service, command path, network discovery or remote access is included.

### Local-network permission forward-compatibility

This preview targets API 35, so no separate local-network runtime permission is currently required for its explicit TCP connection. Android's current guidance requires `ACCESS_LOCAL_NETWORK` for outgoing TCP to LAN addresses when an app targets Android 17/API 37 or later. Before raising target SDK to 37+, add a runtime permission request only when the user chooses TCP, explain the access, and handle denial/revocation as a disconnected state. Recheck the [official local-network permission guidance](https://developer.android.com/privacy-and-security/local-network-permission) before changing target SDK; enforcement details may evolve.

## Architecture proposal
One native Kotlin Android APK, conventional lightweight Android Views/XML, minimal dependencies, no embedded Python runtime, WebView framework, cloud account or AI. Keep Python reference monitor and shared language-neutral protocol fixtures as diagnostic/oracle; do not rewrite working Python tools. One device owns the grill transport at a time (TCP single-client community report). First Android POC direct read-only TCP or BLE with explicit selection; no competing automatic connection. Tablet is the preferred owner when at home. Phone can take over only after tablet disconnects, or later consume an authenticated private-LAN telemetry endpoint from tablet/gateway. Never assume two independent connections work; do not implement unauthenticated LAN serving. Home Assistant or separate always-on hub can become gateway later if Android process lifecycle/reliability warrants it. Factory controller retains all safety-critical regulation.

## Scope and acceptance
- POC: demo and fixture parity with Python, explicit IP or BLE selection, pit and both probe temperatures/targets, clearly reported alarm/fan mode, unavailable on stale/disconnect. No commands. Test Android 10/11 legacy BLE permissions versus Android 12+ Nearby Devices permissions; request only needed permissions and explain them.
- MVP after physical cold-grill validation: responsive phone portrait and tablet landscape UI, large readable Celsius, connection/last-seen state, simple reconnect, optional local timers/alerts with clear notification limitations, no cloud dependency. Optional keep-screen-on only during an active session; idle dim/screen off. Background monitoring if required uses Android-appropriate user-started connected-device foreground service with visible notification; test screen-off, battery optimisation, process death, OS restart; never imply alerts are guaranteed.
- Performance goals (proposed, measure on actual Lenovo): release APK <=15 MB where practical, cold start <=3 s, steady app PSS <=80 MB, ~1 Hz updates only when necessary, bounded history, no continuous BLE scan or animations, no unnecessary services. Measure with adb dumpsys meminfo and startup timing; revise goals from actual results. No benchmark claims yet.
- Later: user-approved cold target-setting experiment only after physical acceptance; no remote manual fan, power, timer or alarm-silencing commands in MVP. Keep future IoT devices behind small capability interfaces; no general IoT platform yet. Prefer existing Home Assistant for broad integrations over custom protocol implementations.
- Tablet placement indoors/dry, away from heat/grease; inspect battery, use appropriate charger and supported charge limit if present. Not a safety controller; loss of app/tablet must not affect grill.
